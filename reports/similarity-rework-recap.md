# Similarity-Match Rework — Recap Report

**Period:** 2026-09-04 → 2026-09-05

It started with an audit. Reading the matcher end to end showed a system that mostly worked but could not explain itself: item texts were mixed with machine codes and serial numbers before comparison while the knowledge-base side had none of that, so scores came out systematically too low — one item scored 0.14 against its own knowledge row. The admin test screen measured differently from production, the stopword list impoverished stored keywords, manual knowledge entries bypassed keyword building entirely, and the confidence-threshold table in the database turned out to be dead configuration nobody reads. Most consequentially, every coder confirmation was stored at near-maximum confidence, giving single human votes permanent power to auto-classify future items.

The first fix replaced the flat stopword list with a tiered token policy: protected domain words that are never dropped, true function words that always are, a small hand-picked canonical map instead of a generic stemmer, and noise rules for serial-like digits. The text normalizer was left byte-identical so rule matching could not change behavior silently. Fifty-three unit assertions guard the policy. Existing keywords were then backfilled across twenty-one of thirty-eight knowledge rows, additively — nothing ever removed except function words and noise — which also exposed manually entered rows containing raw unnormalized phrases, confirming the bypass the audit had flagged.

Evaluation on thirteen coder-reviewed items then surfaced the sharpest problem: identical titles carrying different verdicts. A senior review session established that every conflict came from smoke-test work orders, not genuine expert disagreement, and three canonical verdicts were approved and applied while the overruled rows were retired. Around the same time the scorer learned two new tricks from live user reports: plurals are folded to singular, letter-pair comparison rescues spacing variants like "Merge Point", and the title is now scored on its own so long descriptions can support a match but never dilute it. All four reported variants now auto-classify while genuinely novel text still routes to human review.

The analyze flow was then made incremental because re-classifying everything on every run could not scale: reference data loads once, only items whose fingerprint or knowledge-base version changed are re-scored, human verdicts are never touched, and match records are replaced instead of piled up. Editing an item's text now returns its parent work order to Draft automatically, and the interface shows per-item stale-grey badges with an inline re-analyze action instead of a transient banner — the staleness flag computed server-side by the exact same rule the recalculation uses. Two cleanups followed under explicit approval: four smoke-test work orders deleted with all their dependents, and twenty-six orphaned knowledge rows removed while the three adjudicated canonicals and five live-learned rows were kept.

Left deliberately open: the ML stack is undecided and nothing ML-shaped was installed; seeding the eleven curated per-level reference rows was proposed but not executed; thresholds stay at 0.60/0.35 until at least fifty labeled items exist; disagreement arbitration waits on data and on a correction path for machine verdicts, which still does not exist. The evaluation baseline is currently empty since its ground truth left with the deleted test orders, and will rebuild naturally as new reviews arrive. A grant-access validation bug (text user id sent where an integer was required) was fixed along the way.
